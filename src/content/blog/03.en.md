## Introduction

The Open/Closed Principle states that code should be open for extension, but closed for modification.

In React, this doesn’t mean avoiding changes, but designing components that can evolve without needing constant modification.

In practice, the problem usually appears when we start adding conditional logic to cover new cases.

## The core idea

A component stops scaling well when every new behavior requires modifying its code.

A typical case:

```jsx
const PostBody = ({ post }) => {
  if (post.type === "image") {
    return <ImagePost post={post} />;
  }

  if (post.type === "video") {
    return <VideoPost post={post} />;
  }

  return <TextPost post={post} />;
};

At first it works.

But as new types appear:

- more ifs
- more coupling
- more chance of breaking something that already works

The signal isn't the first conditional.

The signal is when we start repeating the pattern.

## Practical example

One way to improve this is to move the decision out of the component and favor extension over modification.

```jsx
const postComponentByType = {
  image: ImagePost,
  video: VideoPost,
  text: TextPost,
};

const PostBody = ({ post }) => {
  const Component = postComponentByType[post.type] || TextPost;
  return <Component post={post} />;
};
```

Now, adding a new type does not require changing `PostBody`, but extending the configuration instead.

```jsx
postComponentByType.audio = AudioPost;
```

## On using ...props

The props spread (`...props`) is often used to "make a component more flexible."

This can be useful in:

- low-level components (inputs, buttons, wrappers)
- design systems
- components without domain logic (note: domain logic is what something does, not how it is displayed)

But in business/domain components it can be a warning sign:

- the API stops being explicit
- the contract becomes fuzzy
- coupling increases

It's not about never using it, but using it where it really makes sense.

## Final thoughts

OCP isn't about avoiding changes at all costs.

It's about designing so that changes don't break what already works.

In React this often means:

- prefer composition over conditionals
- isolate responsibilities
- make APIs explicit

> **The first if is not a problem.**

> The second or third one is probably a signal.

## Guiding questions to apply OCP in React

- Does adding a new behavior require modifying this component?
- Are conditionals growing?
- Could this be extended without touching existing code?
- Does this component make domain decisions?
- Is the API explicit or too permissive?
