## Introducción

El Open/Closed Principle dice que el código debe estar abierto a extensión, pero cerrado a modificación.

En React, esto no significa evitar cambios, sino diseñar componentes que puedan evolucionar sin tener que modificarse constantemente.

En la práctica, el problema suele aparecer cuando empezamos a agregar lógica condicional para cubrir nuevos casos.

## La idea central

Un componente deja de escalar bien cuando cada nuevo comportamiento requiere modificar su código.

Un caso típico:

```jsx
const PostBody = ({ post }) => {
  if (post.type === 'image') {
    return <ImagePost post={post} />;
  }

  if (post.type === 'video') {
    return <VideoPost post={post} />;
  }

  return <TextPost post={post} />;
};
```

Al principio funciona.

Pero a medida que aparecen nuevos tipos:

- más if
- más acoplamiento
- más riesgo de romper algo existente

La señal no es el primer condicional.

La señal es cuando empezamos a repetir el patrón.

## Ejemplo práctico

Una forma de mejorar esto es mover la decisión fuera del componente y usar extensión en lugar de modificación.

```jsx
const postComponentByType = {
  image: ImagePost,
  video: VideoPost,
  text: TextPost,
};

const PostBody = ({ post }) => {
  const Component = postComponentByType[post.type] || TextPost;
  return <Component post={post} />;
};
```

Ahora, agregar un nuevo tipo no requiere modificar PostBody, sino extender la configuración.

```jsx
postComponentByType.audio = AudioPost;
```

## Sobre el uso de ...props

El spread de props (...props) muchas veces se usa para “hacer el componente más flexible”.

Esto puede ser útil en:

- componentes de bajo nivel (inputs, botones, wrappers)
- design systems
- componentes sin lógica de dominio (ojo! la lógica de dominio es el qué hace, no el cómo se muestra )

Pero en componentes de negocio **puede ser una señal de alerta**:

- la API deja de ser explícita
- el contrato se vuelve difuso
- aumenta el acoplamiento

No se trata de evitarlo siempre, sino de usarlo donde realmente tiene sentido.

## Reflexiones finales

OCP no se trata de evitar cambios a toda costa.

Se trata de diseñar para que los cambios no rompan lo que ya funciona.

En React, muchas veces eso implica:

- preferir composición sobre condicionales
- aislar responsabilidades
- hacer explícitas las APIs

> **El primer if no es un problema.**

> El segundo o tercero, probablemente sí sea una señal.

## Preguntas guía para aplicar OCP en React

- Agregar un nuevo comportamiento implica modificar este componente?
- Están creciendo los condicionales?
- Podría extenderse sin tocar código actual?
- Este componente toma decisiones de dominio?
- La API es explícita o demasiado flexible?
